# GitHub 开源项目选型评估

## 目标

围绕用户要做的产品或系统，找到真实可用的 GitHub 开源候选，基于最新证据判断：

1. 项目是否仍在维护；
2. 部署是否麻烦；
3. 哪些功能可以直接复用；
4. 哪个项目最适合二次开发；
5. 应该直接使用、基于现有项目修改，还是自行开发；
6. 最简单、可验证的 MVP 是什么。

本技能用于调研和决策。除非用户另行授权，不写业务代码、不部署、不 Fork 仓库，也不修改用户项目文件。

## 开始前

先提取产品目标、核心用户、必须功能、部署环境、团队技术栈、预算/许可证限制与不接受的依赖。用户只给出“XXX”或目标含糊到会显著改变候选范围时，先询问实际要做什么；其余信息缺失时可以列出少量明确假设并继续调研。

如果用户提供了指定仓库，必须纳入评估，但仍可寻找更合适的对照项目。若用户指定候选数量、语言、框架、许可证、部署方式或数据驻留要求，以用户约束为准。

## 搜索与取证

必须联网获取当前信息。优先使用 GitHub 仓库主页、README、LICENSE、发布页、提交记录、贡献者、Issue、PR、安装/部署文档和项目官网；只有在一手资料不足时才使用可信的二手资料。为候选提供可点击的仓库链接，并让重要的时效性结论紧邻来源。

先广泛搜索，再筛出通常 3–5 个真正可比较的候选。不要用 Star 数替代产品适配度或维护健康度。排除明显不满足核心需求、许可证不可接受、只是演示代码、与目标层级不一致，或缺乏可运行路径的项目，并简短说明关键排除理由。

不要猜测缺失事实。无法验证的内容标为“未确认”，同时说明它对决策的影响。

## 评估框架

### 维护状态

综合判断，而不是只看最后一次提交：

- 最近提交和正式版本的时间、频率与连续性；
- Issue/PR 是否有近期响应、合并或关闭；
- 活跃贡献者数量、是否高度依赖单一维护者；
- 安全修复、依赖更新、CI 状态和弃用/归档信号；
- 文档与当前版本是否一致。

给出“活跃维护 / 低频维护 / 基本停滞 / 已归档 / 证据不足”之一，并写明证据日期。维护频率应结合项目成熟度判断：成熟稳定项目不必有高提交频率。

### 部署难度

检查官方安装路径、Docker/Compose、环境变量、数据库与外部服务、构建工具链、初始化和升级流程、最低资源需求、身份认证、备份与可观测性。用“简单 / 中等 / 困难”描述，并说明：

- 最短可运行路径；
- 必要基础设施与账号；
- 主要踩坑点；
- 从本地演示到可靠生产部署之间的差距。

不要因为存在 Dockerfile 就直接判定部署简单。

### 功能复用与二开适配

把用户的必须功能映射到每个候选，区分：

- 可直接复用：无需改核心代码即可使用；
- 配置或轻量适配：通过配置、插件、主题或少量集成完成；
- 需要开发：必须修改核心逻辑或新增模块；
- 不适合复用：架构、许可证或产品边界冲突。

同时评估 API/插件机制、模块化程度、测试与文档、技术栈匹配、升级时维护 Fork 的成本、数据模型和扩展点。许可证必须单列；若涉及商业使用、分发、SaaS 或强 copyleft，只做风险提示并建议必要时咨询法律专业人士。

### 决策

分别判断三条路线：

- 直接使用：现成功能已覆盖绝大多数必须需求，配置和集成即可上线；
- 基于现有项目修改：核心能力和架构匹配，缺口有限且 Fork 的长期维护成本可接受；
- 自行开发：候选在关键需求、架构、许可证、安全或运维方面存在结构性冲突。

明确给出一个首选项目和一个备选项目。解释首选项目为什么胜出、它最大的代价是什么、什么条件会让建议改变。避免没有依据的精确工期；若用户要求估算，用区间并写明团队和范围假设。

## MVP 方案

MVP 应验证最核心的用户价值，而不是缩小版完整产品。至少写清：

- 目标用户与单一核心场景；
- 只保留的 P0 功能；
- 直接复用的项目与模块；
- 必须新增或适配的部分；
- 明确暂不做的功能；
- 最简单的部署形态；
- 3–5 条可观察的验收标准；
- 最大风险和一个快速验证办法。

优先选择最少组件、最短闭环和可替换的集成方案。若首选是现有项目，说明如何尽量通过配置、插件或外围服务完成 MVP，以降低核心 Fork 深度。

## 输出方式

先给结论，再给证据。建议采用以下紧凑结构，并根据候选数量调整：

1. 一句话结论：直接用、基于哪个项目改，或自行开发；
2. 候选对比表：维护状态、部署难度、功能覆盖、二开适配、许可证、主要风险；
3. 各候选的关键证据与可复用功能；
4. 首选、备选和不选其他项目的原因；
5. 最简 MVP：范围、复用/新增边界、部署、验收标准；
6. 假设、未确认事项和下一步验证清单。

清楚区分“来源明确的事实”“根据证据做出的判断”和“仍需验证的假设”。结论必须回答用户提出的六项问题，不能只罗列仓库。
